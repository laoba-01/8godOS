## 0. 一张地图

整个项目的启动链,每一级的动作形状**完全相同**:把下一级装进内存、交出控制权。

```
BIOS/UEFI 固件
  └─ GRUB            MBR/ESP 里被固件加载
       └─ 读内核的 multiboot2 头(认出"这是个内核")
            └─ 按 ELF 段把内核搬到 0x100000
                 └─ 进入 32 位保护模式,跳 _start      ← src/boot.asm:18
                      ├─ 校验 EAX == 0x36D76289
                      ├─ CPUID 查长模式支持                ← :33-40
                      ├─ 建 3 张页表,恒等映射前 2MB        ← :42-56
                      ├─ CR3 → CR4.PAE → EFER.LME → CR0.PG ← :58-71
                      ├─ lgdt + 远跳转 0x08:_start64       ← :73-75
                      └─ _start64(64 位)                  ← :81
                           ├─ 设 rsp / 段寄存器             ← :82-89
                           └─ call kmain                    ← :92
                                └─ kmain(C)                ← src/kernel.c:43
                                     ├─ vga_clear()
                                     ├─ idt_init()
                                     ├─ 打印 + 死循环
```

**顺带记住一件事**:GRUB 对你的内核做的这套事,你的内核将来要对用户程序再做一遍 —— 装载、给地址、交出控制权、之后靠中断和系统调用把控制权拿回来。所谓"操作系统",就是这条链上多插了几级。

## M0 — 环境

### 知识点

| 工具 | 职责 | 一句话 |
|---|---|---|
| `nasm` | 汇编器 | 把 `.asm` 变成 ELF64 目标文件 |
| `gcc` | 编译器 | 把 `.c` 变成 ELF64 目标文件 |
| `ld` | 链接器 | 按 `linker.ld` 把 `.o` 拼成一个可执行 ELF |
| `grub-mkrescue`(+ `xorriso`/`mtools`) | 打包 | 生成带 El Torito 引导的 ISO9660 |
| `qemu-system-x86_64` | 执行 | 虚拟机,替你承担"跑挂了要重装"的风险 |

**它们不是"编译器",是流水线上五个不同的工位。** 报错先看是哪个工位报的 —— `undefined reference` 是链接期(`ld`),`implicit declaration` 是编译期(`gcc`),`symbol not defined` 是汇编期(`nasm`)。这一条能省掉大量瞎找。

### 本项目的关键约束:`-nostdlib`

`Makefile:20` 的 `LDFLAGS := -nostdlib` 意味着:

- 没有 libc,没有 `printf`、没有 `malloc`、**没有 `vsnprintf`** —— 所以 `vga_printf` 必须自己 `va_arg` 逐字符吐(`src/vga.c:156-247`)。
- 程序入口不是 `main`,是 `_start`(`linker.ld:2` 的 `ENTRY(_start)`)。因为启动文件(crt0)也不链接。

**但有些头文件仍可用**:`<stdint.h>`、`<stddef.h>`、`<stdarg.h>` 是**编译器自带**的(freestanding 头),不是 libc 的。`vga.c` 用了 `stdarg.h`,`idt.h` 用了 `stdint.h`/`stddef.h` —— 这就是分界线:**头文件能用,库函数不能用。**

## M1 — 能引导

### 知识点

**multiboot2 头是一份合同**(`src/boot.asm:1-12`):

```asm
dd 0xE85250D6                                   ; 头魔数:我遵守 multiboot2
dd 0                                            ; 架构:i386 保护模式
dd multiboot2_header_end-multiboot2_header      ; 头长度
dd -(0xE85250D6+0+(multiboot2_header_end-multiboot2_header))  ; 校验和
dw 0
dw 0
dd 8                                            ; 终止 tag(type=0, size=8)
```

- **校验和那行的来历**:这四个 32 位数相加必须等于 0(模 2³²)。所以第四项就是前三项的相反数,写成 `-(...)` 而不是硬编码一个魔数。
- **头必须落在外镜像的前 32768 字节内**。做法:`section .multiboot2` 单独成段,`linker.ld` 里把它排在所有段之前 —— 这就是"为什么第 1 行要单独 section"的答案。
- GRUB 跳进 `_start` 时:**`EAX = 0x36D76289`(引导魔数)**、**`EBX = multiboot2 信息结构指针`**。头魔数和引导魔数是两个不同的数,别混(`0xE85250D6` vs `0x36D76289`)。
- `linker.ld` 决定布局:`. = 0x100000` 设起始地址,`ENTRY(_start)` 指定入口,段顺序决定文件内布局。

### 一个现存的事实(以后会咬人)

`_start` 只在 `boot.asm:20` 用了 `EAX` 校验,而 **`EBX`(GRUB 给的信息结构指针)从未被保存**;随后 `:33` 起的 `cpuid` 指令**会破坏 EBX**。也就是说,**那份内存映射表的信息目前是丢掉的**。

现在没有内存管理,丢了也无所谓。但一旦要做物理内存管理(知道哪些物理页可用),第一步就是回头把 `EBX` 存到内存里。**记住这个位置**。

## M2 — 进入长模式 ★ 含金量最高

### 知识点

**(1) 三种模式的演进与"为什么必须先保护模式"**

实模式(16 位,1MB,无保护)→ 保护模式(32 位,段基址+限长+DPL)→ 长模式(64 位)。长模式不是独立的一档,它是**保护模式的扩展**:IA-32e 仍用同一套描述符表和特权级模型。所以"进长模式要先把保护模式建好"不是流程规定,是结构决定的。

**(2) 长模式的硬性前置条件:分页必须开**

保护模式下分页是可选的;**长模式下 `CR0.PG` 必须是 1**。这解释了一件反直觉的事:你写的第一个页表不是"为了用虚拟内存",而是"不开就进不了 64 位"。

**(3) CPUID 查能力,是个两步动作**(`boot.asm:33-40`)

```asm
mov eax, 0x80000000   ; 问:最大扩展叶号是多少?
cpuid
cmp eax, 0x80000001   ; 不够就说明没有长模式的叶
jb .error
mov eax, 0x80000001   ; 再问:这一叶的 EDX 里 bit29 = LM 位
cpuid
test edx, 0x20000000
jz .error
```

**两步是必须的**:先确认要查的叶存在,再查那一位。少了第一步,在老 CPU 上会读到垃圾。

顺带看 `boot.asm:22-31` 那 6 行 —— 它在用 EFLAGS 的 **ID 位(bit21)** 探测"这台机器到底支不支持 CPUID"(翻转、写回、读回,变了才说明有 CPUID)。这段在现代机器上是冗余的,但它是"**用一条指令的副作用去探测硬件能力**"的经典手法,值得认识。

**(4) 四级页表与 2MB 大页**(`boot.asm:42-56`)

| 项 | 数 |
|---|---|
| 每张表 | 4096 字节 = 512 项 × 8 字节 |
| 虚拟地址拆分 | 9 + 9 + 9 + 9 + 12 = 48 位有效 |
| 清零 | `rep stosd` 3072 次 = 12 KB = 3 张表 |
| 映射 | `pd[0] = 0x83` → **2MB 大页**,恒等映射 `0x0 ~ 0x200000` |

`0x83` 三个位:`bit0 P=1`(存在)+ `bit1 RW=1`(可写)+ `bit7 PS=1`(这是一页 2MB,别再往下走 PT)。中间两级表项用 `0x003`(P+RW,没有 PS —— 所以要继续往下查)。

**为什么用 2MB 大页**:一张 PD 就覆盖 2MB;若用 4KB 页,得再建 512 张 PT 表。省事,也省内存。

**内核为什么必须落在 2MB 内**:恒等映射只覆盖前 2MB —— 内核在 1MB(`linker.ld:5`)、显存在 0xB8000(752KB)、栈和页表都在 `.bss` 里跟着内核走,全都在 2MB 以下。**这条"2MB 天花板"是当前设计最硬的一个约束**,以后内核变大(或者把栈调大)时它第一个爆。

**(5) 切换序列,顺序不可错**(`boot.asm:58-75`)

```
mov cr3, pml4        ; 1. 页表根先就位(此时还不起作用)
or  cr4, 0x20        ; 2. CR4.PAE=1    —— 不开 PAE 就没有四级页表
rdmsr/wrmsr 0xC0000080, or 0x100   ; 3. EFER.LME=1
or  cr0, 0x80000000  ; 4. CR0.PG=1    —— 分页真的开起来了
lgdt [gdt64_ptr]     ; 5. 64 位 GDT
jmp 0x08:_start64    ; 6. 远跳转,CS 重载,CPU 进入 64 位语义
```

几个"为什么":

- **CR3 为什么在 PG 之前**:`mov cr3` 本身不切换任何东西,它只是把根地址放好;真正生效是 `CR0.PG=1` 那一刻。顺序反了就是"分页开了但根地址是垃圾"。
- **EFER 只能用 MSR 访问**:它不在 CRx 寄存器组里,只能 `rdmsr`/`wrmsr`。MSR 号 `0xC0000080`,LME 是 bit8。
- **为什么必须远跳转**:普通 `jmp` 不重载 CS。只有远跳转(`jmp sel:off`)会让 CPU 用新的 CS 描述符重新解释当前模式 —— **这一步才是"真的进 64 位"**。`0x08` 就是 GDT 里的代码段选择子(第 1 项 × 8)。

**(6) 自举(bootstrap)问题 —— M2 最值钱的一句话**

**打开开关的那一瞬间,代码自己也在开关的影响之下。**

- 开分页那一刻,CPU 已经在按页表翻译地址了;所以**在开之前就必须把当前正在执行的地址映射好** → 这就是必须**恒等映射**的原因。不做,`CR0.PG` 一置位,下一条指令就取不到,直接 triple fault。
- 同理,远跳转之前的代码必须还是 32 位的,远跳转之后才是 64 位的。

这个形状在后面反复出现:**任何"全局生效的开关",都必须保证开关生效时,自己处在合法的状态**。

**(7) GDT 的两项**(`boot.asm:96-104`)

```
dq 0x00AF9A000000FFFF    ; 代码段
dq 0x00AF92000000FFFF    ; 数据段
```

拆开看高 8 字节 `0x00AF9A00`:

| 位段 | 值 | 含义 |
|---|---|---|
| bits 40-47 (access) | `0x9A` | P=1, DPL=0, S=1, type=1010(可执行/可读) |
| bits 48-51 | `0xA` | limit 高 4 位 |
| bits 52-55 (flags) | `0xF` | AVL=1, **L=1**, **D/B=0**, G=1 |

- **L 位(bit 21)= 1 且 D/B = 0** → 这是"64 位代码段"的标记。在长模式下,CPU 靠这两位区分"这是 64 位代码段"还是"这是兼容模式的 32 位段"。
- **limit(0xFFFF) 在长模式下被忽略** —— 段限长检查在 64 位下不做了,平坦模型是硬性的。
- 数据段那项沿用了同一组 flags(含 `L=1`)。长模式下**只有代码段的 L 位有意义**,数据段这一位被忽略,所以照抄无害 —— 但这正是"能解释每一行"会被问到的地方:**抄来的常量如果不追问,就成了黑盒**。
- **为什么还要 GDT**:长模式里段寄存器不能是"基址+限长",只能当**选择子**(指向 GDT 的一项),所以 GDT 必须存在(尽管它管的事少了)。这是"抽象降级但仍然保留"的好例子。

**(8) `.bss` 与"没清 BSS"这个遗留项**

`.bss` 里放的是未初始化/零初始化的全局变量(`boot.asm:106-113`:3 张页表 + 16KB 栈)。它的特点:**不占文件空间**,ELF 里 `p_memsz > p_filesz`,由加载器(GRUB 的 ELF 加载器)负责零填充。

`计划书.md` §4 的流程图里写着"`_start64` 清空 `.bss` 段",但 **`boot.asm:81-92` 里没有这段代码** —— 这是文档与代码不一致(已登记为 M6 遗留项)。现状靠 GRUB 兜着,但自举正确性应当自己负责。

## M3 — VGA 打印

### 知识点

- **MMIO(内存映射 I/O)**:`0xB8000` 不是 RAM,是**显存被固定在物理地址空间里的一块窗口**。写这块地址 = 操作硬件。这是**驱动最原始的形态**:没有"驱动接口",只有一个地址。
- **文本模式显存格式**:80×25,每字符 2 字节 —— **低字节 ASCII,高字节属性**。偏移 =(行 × 80 + 列) × 2。属性 `0x07` = 高 4 位背景(0=黑)、低 4 位前景(7=浅灰)。
- **`volatile` 为什么必须加**(`vga.c:14`):编译器不知道这块内存会被硬件或其他主体改动。不加 `volatile`,一串"写了又没读"的写操作可能被当成死代码优化掉。
- 洞察:**"写内存"和"操作硬件"可以是同一件事** —— 反过来,后面 M5 会看到一个设备**两种访问方式**(显存走 MMIO,光标走端口 I/O)。

2. 字符 `'A'` 配黑底白字,那 2 字节具体是什么?

## M4 — 构建

### 知识点

- **Makefile 的依赖是"为什么能只重编一个文件"的依据**(`Makefile:29-42`):每个 `.o` 依赖自己的 `.c` + 它 `#include` 的头。头改了,依赖它的 `.o` 重编 —— 这就是为什么 `vga.h` 一改,`kernel.o`/`vga.o`/`idt.o` 都要重编。
- `.PHONY`、`$@`(目标)、`$<`(第一个依赖)、`| $(BUILD_DIR)`(order-only:目录时间戳变了不算过期,否则改个文件就全量重编)。

**`CFLAGS` 每一项到底在防什么**(`Makefile:17-19`)—— 这组开关是本项目最有信息量的一行:

| 开关 | 防的是什么 |
|---|---|
| `-ffreestanding` | 不假设有宿主环境:入口不是 `main`、不链接 libc、可用 freestanding 头 |
| `-fno-stack-protector` | 不生成对 `__stack_chk_fail` 的调用 —— 那个符号在 libc 里,`-nostdlib` 下链接会炸 |
| `-fno-pie -no-pie` | 不生成位置无关可执行文件(内核地址是固定的) |
| `-mno-red-zone` | **x86_64 SysV ABI 允许叶子函数用 RSP 之下 128 字节而不调整 RSP**;中断会直接踩掉那片区域。内核里必须禁用 |
| `-mno-mmx -mno-sse -mno-sse2` | 不用 SSE 寄存器:内核不保存 FPU/SSE 状态(没配 CR0/CR4 相关位);顺带免掉了 16 字节对齐的强要求 |
| `-mcmodel=large` | 不假设代码和数据在 ±2GB 内寻址 |
| `-Wall -Wextra -O2` | 警告全开 + 优化 |

**`LDFLAGS`**(`Makefile:20`):`-nostdlib`、`-T src/linker.ld`、`-z max-page-size=0x1000`。

最后那个值得单独记:`ld` 默认按 2MB 对齐段,会在段之间留出巨大空洞(文件体积暴涨、段地址跳来跳去)。设成 0x1000 让段紧挨着放 —— **这和"M2 的 2MB 恒等映射"是同一件事的两面**:你的映射只有 2MB,链接布局就不能随便跳。

### 教训(实际踩出来的)

**工具不能住在构建产物目录里。** 取证脚本 `decode_vga.py` 原在 `build/`(`.gitignore` 忽略),一次 `make clean`(`rm -rf build/`)就永久删掉了它和 M5 的全部证据文件 —— 没副本、不在 git、回收站也没有。凡是"丢了要重做"的东西,都不能放在会被批量删除的目录下。

2. 为什么 `-z max-page-size=0x1000` 必须配着 2MB 恒等映射一起想?
3. `Makefile:35` 那行依赖里的 `src/io.h` 有没有用?(改动 `io.h` 会不会触发重编)

## M5 — VGA 终端 ⚠ 我整写,你的缺口

### 知识点

**(1) 终端语义:四个控制字符的准确定义**(`vga.c:90-107`)

| 字符 | 行为 | 边界 |
|---|---|---|
| `\n` | 列归零 + 行下移;到底则滚动 | 列归零是终端约定(而非 POSIX 语义必然),这样 `\n` 单独用也能回到行首 |
| `\r` | **只**把列归零,不动行 | 与 `\n` 拆开是终端历史遗留(`\r\n` 才是标准换行) |
| `\t` | `col = (col + 8) & ~7`,到下一个 8 的倍数;若越界则换行 | 列 78 → 算得 80 → 触发换行 |
| `\b` | `col--`,**不擦字符** | 列 0 时不动(不下溢)。要擦得自己补空格覆盖 |

**(2) 滚动是软件干的**(`vga.c:27-34`)

把第 1~24 行整块复制到第 0~23 行(1920 次拷贝),再清最后一行。**硬件不做这件事** —— VGA 文本模式有"起始地址"寄存器(CRTC 0x0C/0x0D)可以做硬件滚动,但这里没用。这个对比值得记住:**同一个功能,硬件能做也可以软件做,选择决定成本和复杂度。**

**(3) 硬件光标:一个设备,两种访问方式**(`vga.c:46-74`)

- 光标**不在显存里**,在 CRTC 的寄存器组里。访问方式是一对端口:
  - `0x3D4` = **索引口**:先写"我要访问哪个寄存器"
  - `0x3D5` = **数据口**:再读写内容
- **索引口是有状态的**:每写一次数据口之前都要重新选一次。这是端口 I/O 的典型形态,**和 MMIO 的"直接给地址"完全不同**。
- 用到的编号:`0x0A` 起始扫描线 + 关闭位、`0x0B` 结束扫描线、`0x0E` 位置高 8 位、`0x0F` 位置低 8 位。
- `vga_enable_cursor()` 里 `(start & 0xC0) | 0x0E`:保留高 2 位、把低 6 位重写成 `0x0E` = `bit5=0`(**打开光标**)+ 起始扫描线 14。
- **GRUB 交接过来时 bit5 是置上的**(光标被关掉了),所以"只写位置"看不到光标 —— 这是本项目调得最久的一个坑。

**(4) 三条调试教训**

- **"看不见"有三种可能**:没写对、被关掉了(`0x0A` bit5)、闪烁相位。**读寄存器比看屏幕可靠。**
- **光标更新必须放在 `switch` 之后**(`vga.c:105-106`),不能放进分支:`\t` 分支会瞬时把 `vga_col` 顶到 80,那一刻算出的位置落在缓冲区外。
- **越界不崩,不代表没写坏。** 缓冲区只有 4000 字节,越界写的典型表现是"什么都没发生"。

### 自测

1. 硬件光标为什么不显存里?它在哪里、怎么访问?
2. `0x0A` 那个 bit5 是什么?为什么必须先清它?
3. `\b` 会不会擦掉字符?为什么?
4. `\t` 写在列 78 会发生什么?写出计算过程。

## M6 — IDT 与 CPU 异常 ★ 你最大的缺口

### 知识点

**(1) 三种控制流转移**

| 类型 | 同步/异步 | 来源 | 例子 |
|---|---|---|---|
| 异常 | **同步** | CPU 内部,指令执行的结果 | `#DE` 除零、`#PF` 缺页 |
| 中断 | **异步** | 外部设备 | 键盘、定时器(IRQ) |
| 软中断 | 同步 | `int n` 指令 | 系统调用 |

**这个分类不是学术名目,它直接决定了 M6 的边界**:异常是同步产生的、**不受 `IF` 标志影响**,所以全程 `cli` 状态下照样进得来 —— 这就是"不碰 PIC、不执行 `sti`"能自洽的依据。M7 加外部中断时才需要那两样。

**(2) IDT 的结构**(`idt.h:42-53`)

256 项 × 16 字节 = 4096 字节,所以 limit = 4095 = **`0x0FFF`**(`idt.c:98`)。门描述符里 64 位 handler 地址被**拆成低/中/高三段**存 —— 这是 x86 从 16 位门描述符一路兼容过来的历史遗留,不是设计。

`type_attr = 0x8E`(`idt.c:16`):`bit7 P=1`、`DPL=00`、`bit4 S=0`(系统描述符)、低 4 位 `0xE` = 中断门(进入时**自动清 IF**)。`selector = 0x08` 是 GDT 的代码段。

**(3) 栈帧 —— 整个 M6 的重点**(`idt.h:27-40`)

从低地址往高,异常入口的栈长这样:

```
[r15][r14][r13][r12][r11][r10][r9][r8]     ← common stub 压的 15 个通用寄存器
[rbp][rdi][rsi][rdx][rcx][rbx][rax]
[vector]                                    ← stub 压的向量号
[error_code]                                ← CPU 压的,或 stub 补的 0
[rip][cs][rflags]                           ← CPU 压的(ring0 下就这三个)
```

五条必须记住的规则:

1. **哪些异常 CPU 会压错误码**:`8, 10, 11, 12, 13, 14, 17, 21, 29, 30` 共 **10** 个;其余 **22** 个不压。**这是 CPU 的硬性约定,不能按"看起来该不该有"猜。**
2. 不压的那些,**stub 必须先补一个 dummy `0`**(`isr.asm:30-35`)。补它是为了让**栈帧形状统一** —— common 里做的是 `mov rdi, rsp` + 一个固定布局的结构体,栈里少一个 qword,后面所有字段全部错位。**症状:"有些异常正常、有些异常 RIP 完全不对"** —— 这是最难查的一类 bug,因为不是"全错",是一半对一半错。
3. **ring0 → ring0 时 CPU 不压 `RSP`/`SS`**(只有跨特权级才压)。所以 `regs_t` 里没有这两个字段;要显示"被打断的 rsp",只能靠 `(uint64_t)&r->rflags + 8` **推算**,而且必须说清它是算出来的,不是真字段。
4. **`push` 往低地址走,而 `regs_t` 从低地址开始是 `r15`** —— 所以 common 里**先压 `rax`,最后压 `r15`**(`isr.asm:83-97`)。压反了,所有寄存器值整体错位但栈帧大小不变,**照样能跑,只是每个值都张冠李戴**。
5. **20 qword = 160 字节**:15(通用寄存器)+ 1(向量号)+ 1(错误码)= 17,加 CPU 压的 rip/cs/rflags = 20。160 是 16 的整数倍 → **进来时的 16 字节栈对齐被原样保持**;随即 `call isr_handler` 再压 8 字节返回地址,函数入口 `RSP % 16 == 8`,正是 SysV ABI 期望的状态。

   但注意这句话的边界:它只说"**异常入口之后,stub/common 这段不改变原有对齐状态**",**不是"以后任何中断都不用管对齐"**。往 common 里加/减一个寄存器,总数变奇数就得补一次对齐 —— `isr.asm:99-103` 把这段推理写成了注释,就是怕以后忘了重数。

**(4) 汇编侧的细节**

- **`x86_64 没有 `pusha`/`popa`**(32 位才有) → 15 个寄存器手动压、反序弹。
- **`iretq`,不是 `iret`**(`isr.asm:128`)。`iret` 是 32 位的,在 64 位下弹栈的宽度不对。
- **进入 handler 时 `DF`(方向标志)没有保证** → common 里必须 `cld`(`isr.asm:105`)。不 `cld`,后面任何字符串指令(比如 `rep stosd`)会往**反方向**走。
- **恢复路径也写完了**(`isr.asm:111-128`):`pop` 15 个 → `add rsp, 16` 弹掉向量号和错误码 → `iretq`。M6 里永远走不到(全部 panic),但写出来是为了 M7 加 PIC 时"只差加一张函数指针分发表"。
- **NASM 的宏**:`%macro`/`%rep`/`%assign`,`%+` 拼接符号名(`isr_stub_ %+ i`),`dq isr_stub_%+i` 生成地址表到 `.rodata`。**32 个 stub 是同一个形状**,所以用宏生成而不是复制 32 遍 —— 这是"重复代码用生成消除"的第一课。

**(5) `#PF` 的特殊之处**

**缺页的真实地址在 `CR2`,不在错误码里**(`idt.c:60-64` 用内联汇编读 CR2)。错误码只给**访问类型**:P(是保护违例还是页不存在)、W(读还是写)、U(内核还是用户态触发)。所以 panic 里 `vector == 14` 时多打一行 `cr2=`,别的向量不打。

**(6) 让编译器替你守约定**

```c
_Static_assert(offsetof(regs_t, vector) == 15 * 8, "regs_t 与 common stub 压栈顺序不一致");
```

`idt.h:35-40` 一共 6 条。它们的作用是:**谁改了字段顺序、或在 common 里多压一个寄存器,编译期就炸**,不用等到某个异常打出一串莫名其妙的 RIP 再回头查。**"约定要靠强制,不能靠记性"** —— 这是软件工程里最值钱的一条,而它在裸机上体现得最赤裸。

**(7) `vga_printf`(M5 欠账,M6 第 0 步)**

`-nostdlib` 下没有 `vsnprintf`,只能自己 `va_arg` 逐字符吐(`vga.c:156-247`)。几个必须理解的坑:

- **`%c` 必须按 `int` 取值**(`vga.c:195`):变参函数里 `char` 会被**默认实参提升**为 `int`,按 `char` 取(实际上做不到,但按 `short` 之类取)会导致变参区指针走偏。
- **`%%` 不消耗变参**(`vga.c:202-205`):这一路取错,后面**全部错位**。
- **`%d` 处理 `INT64_MIN`**(`vga.c:211`):用 `(uint64_t)(~sv) + 1` 而不是 `-sv`,因为 `-INT64_MIN` 会溢出。
- **`%p` 刻意不同于 glibc**:固定打 `0x` + 16 位零填充,不打 `(nil)` —— 为的是**行为确定、可比对**。
- **`%X` 是实施中补的**:文档里的期望输出是大写 `0x0E`,而按规格只有小写 `%x`。选择是给 printf 补 `%X`(`vga_put_uint` 多一个 `upper` 参数)而不是改文档期望值 —— 这样验收表原样可用。
- **格式串以 `%` 收尾**要防 `for` 的 `p++` 越过 `\0`(`vga.c:241-243`)。

**(8) 验证设计(这部分比代码更值得学)**

- **先证 `lidt` 装的是你的表**:`nm build/kernel.elf | grep ' idt'` 拿到符号地址,QEMU monitor 的 `info registers` 打出的 `IDT=` base 必须和它一致、limit 是 `0x0fff`。这把"装好了"从"看着没崩"变成**可核对的证据**。
- **四条用例各有分工**,不是重复验证:

  | 用例 | 证的是什么 |
  |---|---|
  | `#DE` 除零 | stub 链通(补 dummy 路径) |
  | `#UD` 非法指令 | 再证一条独立的补码路径 |
  | `#GP` 越界段选择子 | **最强判别点**:`error=0x30` 只能是 CPU 压的(就是那个越界的选择子,而 GDT 只有 3 项、limit=23),证明"带码/不带码"两类 stub 没分反 |
  | `#PF` 读 `0x300000` | `cr2` 取对了地址 |

- **取证不新写脚本**:`memsave 0xb8000 4000` → `decode_vga.py` 解码 → 文本逐字比对。复用工具链,人只做判读。
- **一次运行只能验一条用例**:`iretq` 会**重新执行那条出错指令**,又会立刻异常。所以用编译期宏 `M6_CASE`(`kernel.c:20`)切换,四次运行。
- **`volatile` 是必须的**:`-O2` 会把 `1/0` 和读 `0x300000` 整条优化掉,表现是"什么都没发生"(`kernel.c:25-27, 36-38`)。

## 串联:M0–M6 的四条主线

前六节是散点,这四条是线。

### 主线 1:自举链

上电 → 固件 → GRUB → 你的内核 → (将来)你的用户程序。**每一级做的事情形状完全一样:把下一级装进内存,交出控制权。**

而"交出控制权之后怎么拿回来",就是中断和系统调用的全部故事 —— 所以 M6 不是终点,它是在为"拿回控制权"铺路。

### 主线 2:抽象 = 一张表 + 硬件帮你查

| 表 | 用什么查 | 查到什么 |
|---|---|---|
| GDT | 段选择子 | 段的基址/权限 |
| IDT | 中断向量号 | 处理函数的地址 |
| 页表 | 虚拟地址 | 物理地址 |

这三张表**形状完全一样**:一张连续的表、一个硬件规定的索引格式、CPU 在关键路径上替你做一次查表。

**看懂这条,后面的东西全是同一个套路**:系统调用表(系统调用号 → 处理函数)、文件描述符表(fd → 文件对象)、进程表(pid → PCB)、页框分配器的位图(页号 → 空闲位)。所谓"操作系统设计",一大半是**设计表 + 规定索引**。

### 主线 3:软件必须补上硬件省掉的东西

| 硬件省掉的 | 软件补回来的 |
|---|---|
| 不压错误码的异常 | stub 补一个 dummy `0` |
| `.bss` 不占文件空间 | 加载器零填充(而你没清 `.bss` → 靠它兜着) |
| 串口/CRTC 的间接访问 | 索引口 + 数据口的两次 `out` |
| 文本模式不做滚动 | 软件搬 1920 项缓冲区 |
| `DF` 无保证、`iret` 不是 `iretq` | `cld`、`iretq` |

**硬件省掉的,软件必须还回去;还的方式不对,症状往往不是崩溃,而是"一半对一半错"** —— 前面那些"极难查"的坑,全在这条线上。

### 主线 4:约定要靠强制,不能靠记性

`_Static_assert(offsetof(...))` 守字段顺序、`20 qword` 写成注释、"压栈总数变奇数就得补对齐"写成注释、`-mno-red-zone` 用编译开关消掉一类风险。

这条线跨的是**软件工程**:凡是"人可能忘"的约定,要么让工具替你检查,要么把它写进代码旁边的注释里。**内核项目把这条凸显出来,是因为这里的约定错一点就 triple fault,反馈太狠。**
